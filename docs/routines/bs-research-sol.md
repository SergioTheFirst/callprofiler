## 1. Что произвести

Единственный deliverable — `docs/research/bs-v2/90-execution-plan.md`. Всё остальное в
`docs/research/bs-v2/` — доказательная база и рабочая память; план на неё ссылается, но читается и
исполняется без неё. Из `docs/research/bs/` переиспользовать БЕЗ повторной работы: `40-data-surface.md`
(факты по коду — перепроверить grep-ом только то, на что опирается план), `10-literature.md` (151
источник), `claims-ledger.md` (как перечень ПОЗИЦИЙ, не как выводы — статусы переоценить под новый Goal).

Контракт плана:
- Задачи `R-01…R-nn` в порядке исполнения; каждая ≤1 рабочего дня, ровно один проверяемый результат.
- Обязательные поля каждой задачи: что · файлы/модули (`src/...`; миграция = запись в
  `db/migrations.py::ALL_MIGRATIONS` + `schema.sql`, последняя — id 10) · как (формула / правило / SQL /
  алгоритм — не «спроектировать») · почему (ссылка на C-n и источник) · данные · тир T0–T3
  (`AGENTS.md` / CLAUDE.md Model Routing) · зависимости R-k · тест (файл::функция) · критерий приёмки
  (число/условие) · условие (`unconditional` | `if E-k → исход`) · rollback.
- **Порядок фаз обязателен:** Фаза A — baseline, работающий для нового пользователя на первом же звонке
  (все задачи `unconditional`, без бокса). Фаза B — уточнения по накопленным данным (опциональны,
  включаются флагом/версией формулы, дефолт — baseline). Фаза C — эксперименты на боксе ТОЛЬКО как
  проверка, что уточнения не портят baseline; ни одна задача фазы A не зависит от фазы C.
- Запрещены: задачи-зонтики; задачи без теста; задачи «исследовать X»; задачи «заморозить/удалить
  существующий механизм» без замены, которая даёт владельцу больше информации, чем было; любая
  зависимость baseline от разметки владельца, `fact_feedback`, `outcome_feedback` или калибровки на
  реальной БД.
- Разделы плана помимо задач: концепция (что измеряем и что НЕ измеряем; честно — что индекс ловит и
  что нет); источники данных (таблицы/колонки, как есть в коде); признаки с формулами и значениями по
  умолчанию для нулевой истории; preprocessing; агрегация (формула индекса с весами и их обоснованием,
  поведение при n=0,1,3,10,100); индекс уверенности (§3); схема БД; где пересчитывается (`graph-replay`
  / `archetypes-fit` / watcher autofit; GPU-порядок; replay-инвариант `graph.md` сохранён); versioning
  (`bs_formula_version`, `PROMPT_VERSION` — bump только в фазе B, с канареечной проверкой M4) и миграция
  старых значений; UI (карточка 512 байт, досье, digest ≤300 симв., без счётчиков) — что именно
  меняется в существующих строках `grade:`/паттернах/advice; валидация (офлайн synth с ground truth
  пиздежа + свойства формулы); acceptance; rollback; место в `docs/sintezdiharea.md` и зависимости;
  открытые риски — каждый с проверкой.
- Каждое решение прослеживается: основание (код/литература) → спор (C-n, кто против) → интерпретация →
  решение → задача → тест → критерий.

## 2. Предмет исследования — сигналы, которые УЖЕ есть

Индекс строится из (перечень обязателен к анализу; что-то отбросить можно только с обоснованием):
- `analyses.raw_response` v2: `structured_facts` с типами `promise|contradiction|emotion_spike|vagueness|
  blame_shift|claim`, `confidence`, `polarity`, `intensity`, `quote`; `bs_score 0–100` и `bs_evidence[]`
  (самооценка LLM, сегодня кормит `contact_summaries.avg_bs_score`/`advice`); `promises[].vague`.
  **Известный дефект (верифицирован):** `graph/repository.py:399-402` схлопывает `vagueness/blame_shift/
  emotion_spike/claim` в `event_type='fact'`, колонка `events.fact_type` объявлена, но не пишется, а
  `graph/aggregator.py:44-51` читает счётчики по `event_type` → 4 из 5 членов `v1_linear` ≡ 0, `bs_index
  ∈ [0,20]`. `broken_promise`/`fulfilled_promise` никто не производит. `who='UNKNOWN'` у всех фактов.
  Verbatim-проверка цитат — только в `graph-replay`, не в боевом пути. **Починка этих дефектов —
  обязательная часть фазы A** (писать `fact_type`, считать по `COALESCE(fact_type, event_type)`,
  выводить broken/fulfilled из `promise_outcomes`/`promises.status`, verbatim в боевом пути).
- `promises` + `events(promise|debt)` + `promise_outcomes(status kept|late|broken|unknown, method det|llm,
  days_late)` — исходы обязательств, det-разрешитель по будущим сегментам (+120 дн.), `contact_reliability`.
- `contact_features` (ROBUST-ось: hedge/directive/question/lexical, формальность, `specificity` B2,
  `request_balance` B5, `tempo` B1; AFFECTIVE: `emotion_palette` B4, `accommodation` B6) — z-score внутри
  юзера; для нового пользователя z не определён → нужны абсолютные дефолты/нормы из synth и литературы.
- `calls.role_fragile` и доля UNKNOWN сегментов, `analyses.parse_status`, `risk_score`, `call_type`.
- `deep_facts` (M8, с `who`), `mention_edges`, `entity_metrics` (все счётчики), `bs_thresholds`
  (перцентили), `risk_thresholds`, `admiralty` (A–F + info-цифра), паттерны `psychology_profiler`.
Для каждого сигнала: что он измеряет на самом деле (с учётом `40-data-surface.md` и литературы),
устойчивость к ASR/ролям, значение при нулевой истории, вес в индексе и почему.

Разграничить (и честно записать в раздел «что НЕ измеряем»): ложь · безразличие к истине ·
ошибка/незнание · уклончивость-вежливость · смена позиции по новой информации · ASR-артефакт как
«противоречие». Индекс НЕ претендует на детекцию лжи; он агрегирует наблюдаемые расхождения
(слово↔дело, слово↔слово, конкретика↔обещание) — формулировка в UI должна это отражать без
диагнозов (`CONSTITUTION.md`, T-23), но **строка индекса на карточке/в досье остаётся**.

Литература — из `docs/research/bs/10-literature.md` (не повторять sweep; дочитать точечно, если план
опирается на то, чего там нет). Ключевое для весов: какие из сигналов имеют хоть какой-то внешний
критерий (исходы обещаний), какие — стиль/жанр (хеджи), какие — самооценка модели (`confidence`,
`bs_score`); веса обязаны это отражать (поведенческие > лингвистические > самооценка), а не быть
«круглыми числами».

## 3. Индекс уверенности 1–100 — без разметки

Семантика: «насколько системе можно верить в индексе пиздежа ЭТОГО абонента», отдельно от самого
индекса. Должен быть вычислим для нового пользователя без единого ярлыка. Минимум, что решить и
оформить задачами `R-*`:
- Определение: что значат 30 / 60 / 90 в терминах наблюдаемого (объём и качество evidence, согласие
  сигналов), не в терминах «доли подтверждённых» (подтверждений у нового пользователя нет).
- Входы с основанием и фальсификатором: число фактов/обещаний с исходом, давность, доля UNKNOWN/
  `role_fragile` в звонках-источниках, `parse_status`, согласие независимых сигналов (поведение vs
  лингвистика vs самооценка LLM), устойчивость по окнам (split-half), verbatim-проверенность цитат.
  Что НЕ поднимает уверенность: число звонков без фактов, длительность, `confidence` LLM сама по себе.
- Формула: чистая функция от хранимых счётчиков; границы 1 и 100; монотонность по evidence; версия.
- Проверка БЕЗ владельца: synth-корпус с заложенным ground truth пиздежа (расширить
  `insight/synth/` генератором structured_facts/promise_outcomes с известной «истиной»): индекс
  восстанавливает заложенные градации (ARI/ранговая корреляция ≥ порог), уверенность растёт с evidence
  и падает с шумом ролей — тесты в CI. Опционально (фаза B/C): split-half согласованность на боксе.
- Отношение к существующему: age confidence 1–100 (`contact_age_estimates`, `age_fusion`) — общий
  контракт семантики; `admiralty` info-цифра — переопределить от нового индекса уверенности, букву
  сохранить; `insufficient_evidence` T-15/T-23 — порог уверенности, ниже которого индекс показывается
  с пометкой «мало данных», но показывается.

## 4. Требования к качеству

- Каждое ключевое утверждение — C-n в `claims-ledger.md` (статус, уровень, механизм, фальсификатор,
  кто против). Позиции прежнего ledger (`docs/research/bs/claims-ledger.md`) переоценить под новый Goal:
  «не измеримо → не делать» больше не довод; довод — «что это даёт владельцу с первого звонка и как
  это проверить на synth/свойствах».
- Каждое утверждение пережило ≥3 независимых попытки опровержения с позиций: статистика (вето на
  число без обоснования), deception research (не смешивать с детекцией лжи), архитектура CallProfiler
  (реализуемость, инварианты replay, GPU), адвокат владельца (ценность с первого звонка, не
  академическая чистота), CONSTITUTION/этика, красная команда. **Адвокат владельца имеет право вето на
  любое «убрать/заморозить/не показывать».**
- Анти-шаблон: вывод принят, если выведен из механизма, назван фальсификатор, названо ≥1 неочевидное
  следствие. `surprise-ledger.md` — где результат противоречит `docs/research/bs/` или картам.
- Каждое число — с источником; факты кода перепроверять grep-ом.
- План прошёл враждебную рецензию (статистика, deception, архитектура, этика, адвокат владельца,
  красная команда): каждое возражение закрыто правкой или оставлено открытым риском с проверкой. В
  конце — проверка, что каждое заявленное свойство выполнено (открыть файл, показать, где).
- Проходы доведения (first-principles; фальсифицируемость; «работает ли это на первом звонке?»;
  противоречия между файлами; ясность для программиста и владельца), пока проход меняет ≥5% или критик
  что-то находит.

## 5. Метод — на твоё усмотрение

Консилиум с явными позициями и протоколом спора, панель из ≥3 независимых дизайнов формулы
(например: «починить v1 и дополнить», «поведенческий стержень + лингвистические поправки»,
«байесовское объединение с приорами из synth/литературы»), раунды до «сухого» состояния, критик
полноты — рекомендовано, не предписано. Меняй алгоритм, если он перестал давать новое; фиксируй в
`99-rounds.md`. Экономь на пересказе, не на опровергателях.
