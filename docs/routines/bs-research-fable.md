> llama-server, ffmpeg — CLAUDE.md dev/run split); `/model fable` → `/effort` ultracode; `git pull`;
> `pip install -e ".[dev]"`; `python -m pytest -q` зелёный. Первой строкой промпта — `+NNNNk` = весь
> остаток 5-часового окна (цель расхода, не потолок). Не запускать параллельно с другой сессией над репо.
> Вставить всё от `+NNNNk` до конца.

```

/goal Конечная цель — чтобы владелец CallProfiler (`[me]`, ~16k русскоязычных телефонных звонков,
GigaAM-транскрипты с ролями OWNER/OTHER/UNKNOWN и хрупкой диаризацией, локальный Qwen3.5-9B на 12GB GPU,
100% local) одним взглядом на карточку/досье значительно лучше понимал абонента — и при этом ВСЕГДА

встроенные в существующую архитектуру:
1. механизм оценки надёжности речи/поведения абонента (сегодня — BS-index `v1_linear`; пересматривается

2. ИНДЕКС УВЕРЕННОСТИ 1–100 — калиброванная мера того, насколько система уверена в своей характеристике

3. ОДИН большой, обоснованный, атомарный план разработки, по которому программист реализует п.1–2 без

Результат этой сессии — именно план (п.3) плюс доказательная база под ним. Код не пишется.

## 1. Что произвести

Единственный deliverable — `docs/research/bs/90-execution-plan.md`. Всё остальное в `docs/research/bs/`
(литература, реестр утверждений, first-principles, вердикт по текущему BS, синтез, пакет экспериментов
для бокса) — доказательная база и твоя рабочая память; план на неё ссылается, но читается и исполняется
без неё.

Контракт плана:
- Задачи `R-01…R-nn` в порядке исполнения; каждая ≤1 рабочего дня, ровно один проверяемый результат.
- Обязательные поля каждой задачи: что · файлы/модули (`src/...`; миграция = запись в
  `db/migrations.py::ALL_MIGRATIONS` + `schema.sql`) · как (формула / правило / SQL / алгоритм — не
  «спроектировать») · почему (ссылка на утверждение C-n реестра и источники) · данные · тир T0–T3
  (CLAUDE.md Model Routing) · зависимости R-k · тест (файл::функция) · критерий приёмки (число/условие)
  · условие (`unconditional` | `if E-k → исход`) · rollback.
- Эксперименты для бокса — тоже задачи `R-*`: правило решения записано ДО данных, ветвление
  «исход A → R-x, исход B → R-y». Отдельного «плана для бокса» нет.
- Запрещены: задачи-зонтики («реализовать слой»), задачи без теста, задачи «исследовать X» — дробить
  или переносить в эксперимент с правилом решения.
- Разделы плана помимо задач: концепция (что измеряем и что НЕ измеряем); источники данных; признаки с
  формулами; preprocessing; агрегация и неопределённость; индекс уверенности (§3); схема БД; где
  пересчитывается (`graph-replay` / `archetypes-fit` / watcher autofit; GPU-порядок; replay-инвариант
  `graph.md` сохранён или заменён явно спроектированным эквивалентом); versioning (`formula_version`,
  `PROMPT_VERSION`) и миграция старых значений; UI (карточка 512 байт, досье, digest — ≤300 симв., без
  счётчиков); валидация (офлайн synth + бокс); acceptance; rollback; место в `docs/sintezdiharea.md`
  (после CP-5 / новая T-xx) и зависимости; открытые риски — каждый с экспериментом.
- Каждое решение прослеживается: основание (литература) → спор (C-n, кто против и почему) →
  интерпретация → решение → задача → тест → критерий. Недостаточно доказательств → задача оформляется
  как эксперимент, не как production.

## 2. Предмет исследования

Не «улучшить формулу». Ничто не зафиксировано заранее: ни текущий BS (`graph.md`: 0.40·broken +
0.20·contradiction + 0.15·vagueness + 0.15·blame_shift + 0.10·emotional; гейты confidence≥0.6,
quote≥5; перцентильные `bs_thresholds`), ни число индексов, ни признаки, ни слой graph, ни решение
2026-07-02 «BS-v2 со специфичностью не делать» (`decisions.md`). Пересматривается всё при сильном
основании; инвариант воспроизводимости (граф DERIVED из `events`, детерминированный `graph-replay`)
сохраняется или заменяется явно.

Разграничить и для каждого ответить «способна ли система в принципе отличить»: bullshit · ложь ·
ошибка · незнание · добросовестное заблуждение · уверенность без основания · гипербола · ирония ·
риторика · самопрезентация · манипуляция · ошибка памяти · смена позиции после новой информации ·
уклончивость-вежливость · ASR-артефакт как «противоречие». Запрещённые подмены: неточность→BS,
уверенность→ложь, противоречие→обман, эмоция→ненадёжность, краткость→уклончивость.

Литература: первичные исследования → peer-reviewed → обзоры → мета-анализы; подтверждающие И
опровергающие результаты, effect sizes, переносимость на русскую телефонную речь с ASR-шумом.
Направления: философия BS (Frankfurt, Cohen, Pennycook); deception detection и его провалы (DePaulo,
Bond, Levine TDT, replication); hedging/equivocation (Hyland, Bull, Clayman); LIWC-класс и его критика
на RU; NLP при ASR-шуме (claim / NLI / stance / hedge detection); психометрика (формативные vs
рефлективные индикаторы, validity при малых n); калибровка и decision utility (Brier, reliability
diagrams, cost-sensitive); HCI (one-glance, alert fatigue, false confidence); longitudinal
promise-keeping; паралингвистика (как план для бокса — аудио там есть); русская телефонная прагматика.
`10-literature.md`: ≥60 источников, ≥20 первичных; каждая запись — что утверждает / сила / применимость
здесь / следствие для CallProfiler.

Реконструкция системы по коду — единственная эмпирика на этой машине: `analyze_v001.txt` →
`GraphBuilder` гейты → `fact_id` дедуп → `EntityMetricsAggregator` → `BSCalibrator`/`bs_thresholds` →
`admiralty.source_grade` (+ `promise_outcomes`) → карточка / досье / digest. Рядом: `risk_thresholds`,
`contact_features` (11 осей, 4 тира ASR-устойчивости), `fact_feedback`, `analyses.feedback`,
`role_fragile`, `deep_facts`, `mention_edges`, возрастной конвейер (у него уже есть confidence 1–100:
`contact_age_estimates`, `age_fusion`), bio_* (своё id-пространство), evidence-классы и
`insufficient_evidence` T-15/T-23 (`docs/sintezdiharea.md`). Карты `.claude/rules/*` — первыми, код —
где карты молчат. Synth-корпус (`insight/synth/`) — только демонстрация механизма с пометкой
«synth, не evidence»; реальные результаты не симулировать.

## 3. Индекс уверенности 1–100 (обязательная часть плана)

Величина, отдельная от BS: BS отвечает «что мы думаем об абоненте», индекс уверенности — «насколько
системе можно верить в этой оценке этого абонента». Вывести из первых принципов и литературы по
калибровке, не постулировать. Минимум, что должно быть решено и попасть в план задачами `R-*`:
- Определение и семантика: что значат 30 / 60 / 90; операциональный критерий калибровки (среди
  абонентов с уверенностью ≈X доля подтверждённых утверждений ≈X%); как проверяется на боксе
  (reliability diagram, Brier; weak labels — `fact_feedback`, `promise_outcomes`, `analyses.feedback` —
  с их известной неполнотой и смещением).
- Входы — каждый с основанием и фальсификатором: объём и давность evidence, доля UNKNOWN /
  `role_fragile`, качество транскрипта, согласие независимых сигналов, устойчивость во времени (ICC по
  окнам), статус проверки владельцем, длина истории, тип звонков. Отдельно — что НЕ должно поднимать
  уверенность (много звонков ≠ понимание).
- Уровень: один индекс на абонента и/или на отдельное утверждение (как evidence-классы T-15/T-23)?
  Решить с основанием; при двух уровнях — правило агрегации.
- Отношение к существующему: `admiralty.source_grade` (A–F), age confidence 1–100, evidence-классы
  T-15/T-23, `insufficient_evidence` — унифицировать, подчинить или оставить раздельно; любой вариант с
  обоснованием и задачей миграции.
- Поведение UI при низкой уверенности: что показать вместо цифры BS (порог, формулировка), чтобы не
  создавать ложную уверенность; как владелец поднимает уверенность (feedback-петля, adjudication).
- Детерминизм: чистая функция от хранимых счётчиков, версия формулы, воспроизводится
  `graph-replay`/autofit. Тесты офлайн: монотонность по входам, границы 1 и 100, synth-калибровка;
  бокс: калибровочный эксперимент с правилом решения.

## 4. Требования к качеству — свойства результата обязательны, способ достижения твой

- Каждое ключевое утверждение имеет id C-n в `claims-ledger.md`: статус (converged / contested /
  dissent / retracted), уровень (доказано / хорошо поддерживается / вероятно / гипотеза / неизвестно),
  механизм, фальсификатор, кто против и почему. Minority reports сохраняются, не сглаживаются;
  «сойтись на среднем» между несовместимыми позициями запрещено.
- Каждое ключевое утверждение пережило независимые попытки опровержения с ≥3 разных дисциплинарных
  позиций из набора: эпистемология BS; deception research (роль — доказывать, что cues не работают);
  русская телефонная прагматика; NLP/ASR; психометрика; статистика (вето на любую количественную
  формулировку); HCI; longitudinal поведение; архитектура CallProfiler (реализуемость, инварианты);
  адвокат владельца (ценность, не score); CONSTITUTION/этика (не trust score, не диагноз); красная
  команда (groupthink, шаблонность).
- Анти-шаблон: вывод принят только если выведен из механизма, назван фальсификатор, названо ≥1
  неочевидное следствие, и красная команда не показала, что это общее место. `surprise-ledger.md` —
  выводы, противоречащие прежним планам (`ozalupennieStrategic5.md`, `OzaluplivanieFable2.md`,
  `graph.md`); пустой ledger = подозрение на шаблонность, объяснить письменно.
- Каждое число — с источником. Отчёт субагента — не доказательство: ключевые утверждения перепроверь
  сам по источнику/коду.
- План прошёл враждебную рецензию (попытка ОТКЛОНИТЬ его с позиций статистики, deception research,
  архитектуры, этики, красной команды): каждое возражение закрыто правкой или оставлено в плане как
  открытый риск с экспериментом. В конце — `superpowers:verification-before-completion`.
- Deliverables доводятся проходами (first-principles; фальсифицируемость; анти-шаблон; противоречия
  между файлами и с ledger; ясность для программиста и для владельца; «лучший рецензент журнала»), пока
  проход меняет ≥5% или критик что-то находит. Ограничитель — критерий, не бюджет.

## 5. Метод — на твоё усмотрение

Как организовать работу, решаешь сам: консилиум экспертов-агентов с протоколом спора, judge panel из
≥3 независимых дизайнов, раунды loop-until-dry, multi-modal литературный sweep, completeness critic —
всё доступно (`Workflow`, `/loop`, `deep-research`, `superpowers:brainstorming`, `grill-me`,
`planning-with-files`, веб) и рекомендовано, но не предписано по шагам. Меняй алгоритм по ходу, если он
перестал давать новое; выбор и причину фиксируй в `99-rounds.md`. Бюджет `+NNNNk` расходуй полностью на
ширину источников, число опровергателей и проходы доведения — не на перечитывание и пересказ.

## 6. Границы, память, финал

- Ничего в `src/`, никаких миграций, никакого production-кода. Ни одного фрагмента данных владельца в
  веб-запросы (их здесь нет — правило действует). Никаких выводов о «личности», диагнозов, типологий —
  только наблюдаемые паттерны с границами (CONSTITUTION, T-23, инв. 23/29).
- `docs/research/bs/` — единственная память (компакция контекста): `00-README.md` (индекс, статус,
  расход), `claims-ledger.md`, `surprise-ledger.md`, `10-literature.md`, `20-first-principles.md`,
  `40-data-surface.md`, `60-existing-bs-verdict.md`, `70-synthesis.md`, `90-execution-plan.md`,
  `99-rounds.md`, `box-package/` (README с подготовкой бокса: `backup` → `verify-backup` → копия в
  `C:\calls\research\`, watch остановлен, llama-server в LLM-окне; `hypotheses.md`; `protocol.md` —
  exploration/confirmation split контактов, bootstrap на уровне контакта, множественные сравнения,
  sensitivity к доле UNKNOWN; `scripts/*.py` — одна команда, фиксированный seed, НЕ открывают боевую БД,

  Состав файлов можно менять — кроме `90-execution-plan.md`.

задача не начинается со слова «исследовать».
```
