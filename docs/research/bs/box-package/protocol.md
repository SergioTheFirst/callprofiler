# Протокол измерений на боксе

## 1. Единица анализа и кластеры
- Единица исхода — обещание (`promise_key`); единица кластера — `contact_id`. Все bootstrap-интервалы —
  **cluster bootstrap по контактам** (Cameron/Gelbach/Miller 2008, L-130), B=2000, seed=0; интервалы 80%
  (10–90 перцентили) — выбран уровень, соответствующий операционным решениям (не научной публикации);
  везде, где правило решения требует «CI исключает 0», используется 80%-CI.

## 2. Exploration / confirmation split контактов
- `contact_id` детерминированно делятся на **E (exploration)** и **C (confirmation)** по
  `sha1(user_id|contact_id)[0] < '8'` (≈50/50). Все решения о параметрах (`q`, `h`, `w_role`, `tier_cuts`,
  temperature) принимаются по E; отчёт на C — финальная проверка, правила решения применяются к C.
  Если на C < 10 контактов с исходами — split отменяется, решение по всему множеству с пометкой
  «без confirmation» (ограничение, не игнорировать).
- Temporal holdout (E-4/E-8): `T₀ = max(evidence_date) − 180 дней`; обучение — обещания с `call_datetime
  < T₀`, тест — исходы с `evidence_date ≥ T₀`. Утечка: обещание до T₀ с исходом после T₀ — относится к
  тесту (исход — событие после T₀), параметры приора считаются только по исходам до T₀.

## 3. Множественные сравнения
- E-1…E-9 — разные решения, каждое со своим заранее записанным правилом; Bonferroni не применяется
  между экспериментами (решения независимы по смыслу). **Внутри** эксперимента с >1 сравнением
  (E-8: 2 значения h vs ∞; E-9: 2 режима) — Holm-поправка на число сравнений при
  проверке «CI исключает 0» (эквивалент: 80%·(1−α_adj)).

## 4. Sensitivity к доле UNKNOWN
- Каждый отчёт (E-1, E-3, E-4, E-8) дублируется на подмножестве обещаний из звонков с UNKNOWN-долей
  ≤ 0.3 (не role_fragile). Если вывод меняет знак — в отчёте пометка `FRAGILE`, правило решения
  применяется к подмножеству ≤ 0.3 (консервативно).

## 5. Adjudication владельца (E-1, E-2, E-6)
- Один файл `adjudication-request.md` ≤ 40 элементов: ≤30 разрешённых (стратификация: det/llm × kept/
  late/broken, пропорционально, но ≥3 на ячейку где возможно) + ≤10 `unknown` с прошедшим `due` и ≥2
  последующими звонками. Порядок — `random.Random(seed).shuffle`. Для каждого элемента: дата звонка,
  `call_id` (для прослушивания в дашборде), цитата обещания, цитата-evidence исхода (если есть), вопрос.
  **Не показываются:** метод, статус по системе, CI, фраза.
- Владелец отвечает тремя колонками: «было ли это обещание контакта владельцу? (да/нет)» → FP
  извлечения; «исход: исполнено / не исполнено / не знаю»; «роль перепутана? (да/нет)».
- Время на элемент не ограничено; повторная сессия допустима; ответы — `adjudication-answers.csv`
  (`promise_key,is_promise,outcome,role_swapped`), читается скриптом 04.
- Второй раунд (E-6) — отдельный ≤20-строчный запрос, те же правила.

## 6. Калибровочные метрики (E-3)
- Попадание: `|p̂_adj − median| ≤ 0.1`, где `p̂_adj` — доля исполнения по adjudicated исходам контакта
  (только контакты с ≥3 adjudicated). Диаграмма: адаптивные бины по равной заполненности (≥8
  элементов/бин), ECE_adapt = Σ|conf_bin − acc_bin|·n_bin/N; Brier по окну; bootstrap по контактам для
  ECE (80%-CI). Стадия 1 — отчёт предварительный при любом N < 150.

## 7. Воспроизводимость
- Каждый скрипт печатает `seed`, `db sha256[:12]`, версию формулы, параметры; результат — markdown в
  `results/` с этим заголовком. Повторный запуск с тем же seed — идентичный файл (тест `--synth`
  запускается дважды и сравнивает).
