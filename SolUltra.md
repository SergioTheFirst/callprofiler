# AUTONOMOUS PRODUCTION MODERNIZATION

/goal

Модернизируй текущий проект до production-ready уровня.

Работай как автономный senior software architect + senior developer + reviewer + QA engineer.

Твоя задача — не просто реализовать два существующих плана, а **самостоятельно определить, какие их решения действительно правильны, какие ошибочны, что отсутствует, а затем реализовать лучший технический вариант**.

Работа выполняется в две основные стадии:

**STAGE 1 — DEEP ANALYSIS → SYNTHESIS → PLAN**

затем:

**STAGE 2 — IMPLEMENTATION → TESTING → VERIFICATION**

# 3. КРИТИЧЕСКАЯ ПРОВЕРКА ДВУХ ПЛАНОВ

Проведи независимую проверку каждого существенного утверждения из:

`deepseekdiharea.md`

и

`opsus5.md`.

Для каждого значимого предложения выясни:

- существует ли описанная проблема на самом деле;
- подтверждается ли она кодом;
- правильно ли определена причина проблемы;
- действительно ли предложенное решение её устраняет;
- нет ли более простого решения;
- какие побочные эффекты возможны;
- какие зависимости появляются;
- как решение влияет на производительность;
- как решение влияет на надёжность;
- соответствует ли оно архитектуре проекта;
- не противоречит ли `CONSTITUTION.md`.

Классифицируй предложения как:

**ACCEPT** — подтверждено и должно быть реализовано.

**MODIFY** — идея правильная, но реализацию необходимо изменить.

**REJECT** — предложение не подтверждается, избыточно или технически неправильно.

**DEFER** — полезно, но не относится к текущему production milestone.

Не принимай решение на основании авторитета документа.

Основанием является **фактическое состояние проекта + инженерная аргументация**.

# 4. СОБСТВЕННЫЙ DEEP ANALYSIS

После проверки двух планов проведи собственный анализ.

Ищи проблемы, которые могли отсутствовать в обоих документах.

Особенно проверь:

### Architecture
- архитектурные слабости;
- неправильные зависимости;
- чрезмерную связанность;
- дублирование;
- неправильные границы модулей;
- скрытые глобальные состояния;
- проблемы расширяемости.

### Correctness
- ошибки алгоритмов;
- race conditions;
- неправильную обработку edge cases;
- потерю данных;
- некорректные состояния;
- проблемы повторного запуска;
- проблемы после сбоев.

### Reliability
- обработку исключений;
- восстановление после ошибок;
- целостность данных;
- graceful degradation;
- корректное завершение;
- диагностируемость.

### Performance
- CPU bottlenecks;
- memory bottlenecks;
- I/O bottlenecks;
- ненужные вычисления;
- повторную обработку;
- неоправданные аллокации;
- параллелизм;
- кэширование.

### Maintainability
- читаемость;
- тестируемость;
- конфигурацию;
- логирование;
- типизацию;
- документацию;
- технический долг.

### Production readiness
Проверь, что программа сможет нормально работать длительное время, а не только успешно запускаться на одном тестовом примере.

Не добавляй улучшения ради количества.

Каждое изменение должно иметь измеримую или очевидную инженерную ценность.

# 5. RTX 3060 — ЦЕЛЕВОЕ ОБОРУДОВАНИЕ

Код разрабатывается на текущей машине, но выполняться будет на другой машине с:

**NVIDIA RTX 3060.**

Учитывай это при проектировании.

Проверь:

- CUDA compatibility;
- версии PyTorch/CUDA или аналогичных библиотек;
- VRAM limitations;
- CPU/RAM requirements;
- GPU utilization;
- batch size;
- precision;
- memory transfers;
- CPU ↔ GPU overhead;
- multiprocessing/threading;
- потенциальный GPU OOM;
- поведение при отсутствии GPU.

Не оптимизируй систему под гипотетическое оборудование мощнее RTX 3060.

Но и не добавляй GPU-оптимизации там, где они не дают реального выигрыша.

# 6. CONSTITUTION

`CONSTITUTION.md` является важным архитектурным ограничением.

Есть одно правило, которое нельзя нарушать:

> Система должна оставаться исключительно локальной.

Нельзя превращать её в:

- SaaS;
- cloud service;
- удалённый сервис;
- систему, критически зависящую от внешнего API;
- систему, требующую внешней инфраструктуры для основной работы.

Остальные положения `CONSTITUTION.md` разрешается изменить, если анализ покажет, что они препятствуют корректному развитию проекта.

Если необходимо изменить Constitution:

1. объясни противоречие;
2. сформулируй новое правило;
3. сохрани принцип полностью локальной системы;
4. включи изменение в `sintezdiharea.md`;
5. внеси изменение во время реализации.

Не изменяй Constitution без объективной необходимости.

# 7. СОЗДАЙ ЕДИНЫЙ СИНТЕЗИРОВАННЫЙ ПЛАН

После завершения анализа создай:

`sintezdiharea.md`

Это должен быть **главный технический план проекта**.

Он должен содержать только решения, прошедшие проверку.

Для каждого изменения укажи:

- проблему;
- доказательство существования проблемы;
- предлагаемое решение;
- затрагиваемые файлы/модули;
- зависимости;
- риски;
- способ проверки;
- критерий готовности.

Раздели задачи на:

### P0 — CRITICAL
Необходимо для корректности или production-ready состояния.

### P1 — IMPORTANT
Существенное улучшение качества, надёжности или производительности.

### P2 — OPTIONAL
Полезные улучшения, которые не должны мешать завершению основного milestone.

Определи правильный порядок выполнения.

Укажи зависимости между задачами.

**correctness → reliability → performance → simplicity → maintainability.**

После каждого существенного этапа выполняй соответствующие проверки.

Используй доступные инструменты:

- unit tests;
- integration tests;
- smoke tests;
- type checking;
- linting;
- static analysis;
- profiling;
- performance tests;
- реальные тестовые данные проекта.

Если тестов недостаточно — создай необходимые.

Проверяй не только:

> "код запускается"

но и:

> "код делает именно то, что должен делать".

Особенно проверяй regression risk.

---

# 12. ПРОИЗВОДИТЕЛЬНОСТЬ

Если выполняешь оптимизацию, по возможности сначала установи bottleneck, а затем оптимизируй его.

Не оптимизируй код только потому, что он выглядит неоптимальным.

Предпочтительно иметь:

**измерение → изменение → повторное измерение**

вместо субъективного утверждения:

> "теперь это быстрее".

---

# 13. АВТОНОМНОСТЬ

Работай максимально автономно.

Не спрашивай разрешение на обычные инженерные решения.

Самостоятельно принимай решения, если они:

- обратимы;
- находятся в рамках цели;
- не нарушают локальный характер системы;
- не требуют информации, которой нет в проекте.

Запрашивай решение только если:

1. необходимо изменить саму цель проекта;
2. необходимо нарушить принцип полностью локальной системы;
3. требуется необратимое действие с важными пользовательскими данными;
4. требуется внешний ресурс/секрет/доступ, которого у тебя нет;
5. существует несколько принципиально разных архитектурных вариантов с существенно разными последствиями и выбрать между ними невозможно на основании имеющихся данных.

Во всех остальных случаях выбирай лучший инженерный вариант самостоятельно.

# 14. АГЕНТЫ / ПАРАЛЛЕЛЬНЫЕ ЗАДАЧИ

Если среда предоставляет агентов или параллельные execution capabilities — используй их там, где это действительно полезно.

- другой анализирует тесты;
- другой анализирует производительность;
- другой проверяет зависимости.

Но не создавай агентов ради формального выполнения требования "использовать агентов".

Не дублируй одну и ту же работу несколькими агентами без необходимости.

# 15. ИНЖЕНЕРНЫЙ ЦИКЛ

Для каждой существенной задачи используй цикл:

**UNDERSTAND**
→ понять проблему

**INSPECT**
→ изучить код

**DECIDE**
→ выбрать решение

**IMPLEMENT**
→ внести изменение

**TEST**
→ проверить

**VERIFY**
→ убедиться, что изменение действительно решает исходную проблему

**INTEGRATE**
→ проверить отсутствие регрессий

Если проверка обнаруживает проблему — исправь её и повтори цикл.

---

# 16. НЕ ОСТАНАВЛИВАЙСЯ ПОСЛЕ ПЕРВОЙ УСПЕШНОЙ СБОРКИ

Успешный запуск не означает завершение задачи.

После успешной реализации проведи финальный audit:

- соответствует ли код исходной цели;
- реализованы ли P0;
- реализованы ли необходимые P1;
- нет ли очевидных regression;
- нет ли мёртвого кода;
- нет ли незавершённых TODO, созданных в ходе работы;
- нет ли временных костылей;
- соответствует ли код Constitution;
- учитывается ли RTX 3060;
- действительно ли система остаётся локальной.
