# deepseekdiharea.md — план улучшения распознавания и обработки текста

> Статус фактов: все утверждения проверены по источникам 2026-08-07
> (модельные карточки Hugging Face, README репозиториев, код проекта).
> Формат: тезис — ЧТО → ПОЧЕМУ (доказательства) → КАК (шаги, без кода).

---

## Контекст

Текущий пайплайн (из кода и конфига `configs/base.yaml`):

```
аудио → pyannote 3.1 + embedding (ref OWNER/OTHER) → GigaAM v3-RNN-T
        (фиксированные окна 20 c, без VAD) → SQLite → llama.cpp LLM
        (Qwen3.5-9B Q8_0, парсинг JSON 4-уровневым response_parser) → карточки/Telegram
```

Ограничения: 100% локально (Статья 4), RTX 3060 12 GB, GPU-дисциплина
(ASR+pyannote и LLM никогда в VRAM одновременно), Python 3.10, Windows.

## Тезис 1. Пунктуация и нормализация чисел: GigaAM v3-e2e-RNNT вместо v3-RNN-T

**ЧТО.** Перевести ASR с ревизии `GigaAM-v3-RNNT` (RNN-T без пунктуации) на
`v3-e2e-rnnt` — end-to-end модель с автоматической пунктуацией и нормализацией
чисел.

**ПОЧЕМУ.**
- Текущий RNN-T отдаёт текст без знаков препинания и без заглавных (подтверждено
  по коду `src/callprofiler/transcribe/gigaam_runner.py`: используется RNN-T-модель
  из каталога `C:\models\GigaAM-v3-rnnt`).
- В README репозитория `salute-developers/GigaAM` (проверено 2026-08-07)
  заявлено: `v3-e2e-rnnt` даёт пунктуацию и нормализацию чисел на выходе
  (анонсировано в 2025-11 в официальном блоге SaluteAI, зафиксировано в
  `CHANGELOG.md` за 2026-08-07).
- Текст без пунктуации ухудшает: читаемость caller cards, полноту поиска FTS5
  (слипшиеся слова), и качество LLM-анализа (модель вынуждена додумывать
  границы предложений — источник ошибок в summary/промисах).

**КАК.** Скачать ревизию `e2e_rnnt` локально (та же директория моделей),
переключить модель в конфиге (`models.gigaam_model_dir`), прогнать фиксированный
тестовый набор звонков и сравнить: WER + субъективное качество текста.
Изменение изолировано в `gigaam_runner.py`, GPU-бюджет не меняется.
**Риск:** другой декодинг-API (нужен адаптационный слой в раннере); проверить
скорость инференса на RTX 3060.

## Тезис 2. VAD-нарезка по речи вместо фиксированных окон 20 c

**ЧТО.** Заменить нарезку аудио фиксированными окнами (`gigaam_chunk_sec: 20`,
`gigaam_overlap_sec: 0.0`) на нарезку по речевым сегментам VAD
(pyannote/segmentation-3.0, уже в экосистеме проекта).

**ПОЧЕМУ.**
- В коде `gigaam_runner.py` прямо зафиксирован авторский комментарий:
  «Апгрейд на VAD-нарезку — отдельный шаг» — это известный, признанный в проекте
  технический долг.
- Фиксированные окна режут фразы на границах (слово может быть разрезано),
  а `overlap: 0.0` означает потерю контекста на стыках — в тексте появляются
  обрывки и дубли.
- Окна по расписанию захватывают тишину → лишние вызовы инференса и «пустые»
  сегменты в транскрипте, засоряющие FTS и LLM-контекст.
- Ограничение модели — 25 c (`LONGFORM_THRESHOLD` в коде); речевые сегменты
  VAD почти всегда короче 25 c, т.е. ограничение совместимо.

**КАК.** До ASR прогнать аудио через `pyannote/segmentation-3.0` (VAD-режим,
офлайн, без HF-гейта), склеить сегменты с паузами < 0.3 c, подавать каждый
сегмент в GigaAM отдельно. Держать запас на стыках (~0.1-0.2 c на край).
**Проверка:** доля «мусорных» сегментов и обрывков слов в тестовом наборе.

## Тезис 3. Word-level timestamps GigaAM — точная привязка «кто кому сказал»

**ЧТО.** Получить от GigaAM метки времени на уровне слов и сопоставлять слова
с сегментами спикеров вместо текущего overlap-mapping сегмент→спикер.

**ПОЧЕМУ.**
- README `salute-developers/GigaAM` (проверено 2026-08-07): поддержка
  word timestamps появилась в обновлении 2026-04 (`word_timestamps=True` в API
  пакета `gigaam`).
- Сейчас `role_assigner.py` делает грубый overlap-mapping (пересечение
  по времени), а `transcribe_turns` нарезает реплики по границам turn'ов —
  слова на границах перекрёстной речи могут приписаться не тому спикеру.
- Ошибки «кто сказал» напрямую ломают самую дорогую бизнес-логику: промисы
  (кто кому обещал), досье контакта, оценку тона собеседника.

**КАК.** Слова с таймстампами из GigaAM (2026-04+) сопоставляются с сегментами
диаризации (pyannote) по времени центра слова; реплики спикеров пересобираются
из слов. Проверка на тестовых звонках с ручной разметкой «кто говорил».

## Тезис 4. Диаризация community-1 — отложенный апгрейд (решение владельца)

**ЧТО.** Зафиксировать как проверенный кандидат переход
`pyannote/speaker-diarization-3.1` → `pyannote/speaker-diarization-community-1`.

**ПОЧЕМУ (доказательства, model card проверена 2026-08-07).**
- Лицензия cc-by-4.0, гейт — бесплатная авторизация HF; модель работает
  локально через `Pipeline.from_pretrained` → Статья 4 (без облаков) не нарушается.
- DER-выигрыш по бенчмаркам model card (зафиксировано в `CHANGELOG.md` 2026-08-07):
  AliMeeting 20.3 vs 24.5, CALLHOME 26.7 vs 28.5, DIHARD3 20.2 vs 21.4,
  AMI IHM 17.0 vs 18.8, MSDWild 22.8 vs 25.4, VoxConverse =11.2,
  REPERE хуже (8.9 vs 7.9) — единственная регрессия.
- Модель содержит `exclusive_speaker_diarization` — режим согласования таймстампов
  с ASR, т.е. решает тезис 3 на стороне диаризации.
- 949 лайков — высокая встроенность сообщества.
- Дополнительный плюс: уходит жёсткое `min_speakers=2 / max_speakers=2`
  (зашито в `pyannote_runner.py`) — звонки с 3+ участниками (громкая связь,
  конференция) сейчас обрабатываются неправильно.

**КАК.** Пилот: тот же `pyannote_runner.py` с другим `pipeline_name` + настройка
числа спикеров; сравнить DER на собранном тестовом наборе звонков.
**Статус:** владельцем в `/gaol` принято «оставляем 3.1, ничего не меняем» —
этот тезис остаётся в плане как обоснование на случай пересмотра решения.

## Тезис 6. JSON-Schema-грамматика llama.cpp вместо 4-уровневого response_parser

**ЧТО.** Передавать схему ответа LLM как JSON Schema в `response_format`
llama-server — модель будет генерировать гарантированно валидный JSON
с первого раза.

**ПОЧЕМУ (официальный README llama.cpp, проверено 2026-08-07).**
- llama-server поддерживает GBNF-грамматики и конвертацию JSON Schema в
  грамматику: в `/chat/completions` — поле `response_format`
  (`{"type": "json_object", "schema": ...}` / `{"type": "json_schema", ...}`).
  Ограничение выборки сэмплинга грамматикой: валидность гарантируется на 100%,
  повторы запросов не нужны.
- Существование 4-уровневого `response_parser.py` (regex → partial JSON →
  JSONL-склейка → фолбэк) — прямое свидетельство того, что сейчас LLM регулярно
  отдаёт битый/обрезанный JSON: каждый такой случай — повторный запрос или
  потерянный анализ.
- Это самая дешёвая победа: нулевой риск для модели, нет переобучения,
  меняется только клиентский слой `llm_client.py`.

**КАК.**
- Описать `Analysis` (summary, flags, risk_score, priority, feedback...) как
  JSON Schema **с учётом задокументированных ограничений** конвертера
  (README llama.cpp):
  - `additionalProperties` по умолчанию false (это хорошо — меньше галлюцинаций);
  - `minimum/maximum` поддерживаются только для integer → risk_score перевести
    на целые (например 0-100) или валидировать диапазон после;
  - нельзя смешивать `properties` с `anyOf/oneOf` — схема должна быть плоской;
  - `pattern` только в виде `^...$`;
  - не использовать `uniqueItems`, `if/then/else`.
- Сначала замерить baseline: % битых JSON сейчас (по логам parser-фолбэков),
  затем сравнить после включения грамматики. Парсер оставить как фолбэк на
  случай включённого `--json` вручную.

## Что НЕ улучшать (обоснованный отказ)

- **NeMo (NVIDIA)** — несовместим с боксом (только Linux, Python 3.12+, torch 2.7+);
  заменял бы весь стек. Отклонено в `/gaol`.
- **pyannoteAI Precision-2 / Live-1** — облачные сервисы, нарушение Статьи 4.
- **WhisperX** — прямо запрещён CONSTITUTION.md (стр. 78); word-timestamps-
  проблема решается нативными средствами GigaAM (тезис 3).
- **ECAPA-TDNN / wespeaker как основной эмбеддер** — текущая связка
  pyannote 3.1 + embedding работает и замерена; менять без пилота нет смысла
  (community-1 как единый апгрейд покрывает этот пункт).
